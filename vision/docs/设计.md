## 3. 方案选型

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 全模型堆叠 | 斑马线/红绿灯/台阶各训一个检测器 | 需数据集 + CPU 训练，以周计；无合适公开标注 |
| **B. 度量空间 + 混合** | 盲道复用现成 `best.pt`；障碍/红绿灯复用 COCO 预训练；斑马线/台阶用地面反投影后的几何规则 | **采用**。无需标注数据，CPU 可实时 |
| C. 逐帧视觉大模型 | 每帧调 VLM | 1–3 s/帧，无法实时 |

### 核心：地面度量空间（IPM 反投影）

相机按**胸/腰前挂、镜头略前倾向下**安装。针孔模型 + 地面平面假设，闭式反投影：

```
xc = (u - cx) / f
yc = (v - cy) / f
den = yc·cosθ + sinθ
t  = h / den
X  = xc · t                      # 横向偏移(米)，右正
Z  = (-yc·sinθ + cosθ) · t       # 前方距离(米)
```

θ 为俯仰角（光学轴低于水平线的角度），h 为相机离地高度，f 为像素焦距。`den ≤ 0` 即地平线以上，判为无效。

**已验证**（h=1.2 m，pitch=30°，VGA 640×480，hfov=65° → f≈502 px）：

- 画面底边 → 地面 Z = **0.83 m**，X = 0
- 地面上 X=0 / X=0.5 的直线，反投影后分别落在度量网格的**同一列内**，列填充率 91% / 89%
- 度量网格（X∈[-1.5,1.5] m，Z∈[0.6,4.0] m，1 cm/px）有 **85.4%** 落在原图内

因此所有角度/偏移/距离判断在度量空间完成，参照项目的斜率法被彻底替换。

### 行进砖 vs 提示砖

**判据（经实测审计修正后）**：LSD 长线段统计（图像平面即可，投影下直线仍为直线，故透视不变）。

| 砖型 | 长线段数 | 最长线段/对角线 |
|---|---|---|
| 行进砖（长条状平行脊） | **5–35 条**，方向高度一致 | 0.18–0.71（波动大） |
| 提示砖（圆点阵列） | **1–2 条**（圆点边缘太短） | 0.14–0.26 |

**主判据是长线段条数**；`max_len_ratio` **只参与置信度，不作硬门限**。

> 踩过的坑：最初把 `max_len_ratio >= 0.30` 当硬门限，结果对 16 个"全是行进砖"
> 的实测样本，有 6 个被判成 `unknown`——同一段行进砖在不同视角下该值会掉到
> 0.18。修正后 16/16 全对。
>
> 第二个坑：线段极少数时（<3 条）长度才是有区分力的信息，因此在该分支里用
> `max_len_ratio >= 0.30` 反判为行进砖（低置信度 0.45，交给时序确认）。修正后
> 8 个带人工真值的标注样例 **8/8 全对**，该结果已固化为回归测试
> `tests/test_tile_labels.py`。

反例记录（说明为何不用结构张量）：在透视图像平面直接算梯度结构张量的
`vert/horz` 能量比，近处行进砖区只有 1.93，反而低于远处提示砖区的 3.59
—— 透视会破坏纹理统计，故不采用该特征。

### 逐框判别（安全相关）

一帧里可能同时出现行进砖和提示砖，因此**不能只挑面积最大的框**：

- **脚下砖型** `tile_type`：取**最近**的框（框底边最靠画面下方）；
- **前方提示砖距离** `warning_near_m`：取所有提示砖框里距离最小者。

否则"脚下的提示砖"会被"远处更大的行进砖"盖掉，导致漏报路口。

距离一律截断到非负：近景俯视（如手机近乎垂直向下拍）时框底边会投影到相机
**后方**，算出的 Z 为负，在"距离"语义下等价于"脚下 0 米"。

## 5. 检测能力与精度等级

| 能力 | 方法 | 精度等级 |
|---|---|---|
| 盲道存在/范围 | 现成 `best.pt`（`Tactile_Paving`, `Tactile_Paving_Metro`） | 模型级，mAP50 0.678 为**上限** |
| 行进砖 / 提示砖 | LSD 长线段统计 | 已实测可分 |
| 方向 + 横向偏移 | 盲道区域在度量空间拟合中心线 | 几何精确（依赖标定） |
| 障碍物 | YOLOv8n-COCO，框底边反投影求距离 | 模型级 |
| 红绿灯 | COCO `traffic light` 框 + 框内 HSV + 时序投票 | 模型级检测 + 规则级颜色 |
| 斑马线 | 度量空间内白条沿 Z 轴的周期性方波 | 规则级 |
| 台阶 | 地面空间高度不连续 + 时序确认，只报"疑似" | 规则级（保守） |
| 盲道丢失 / 画面质量 | 跟踪丢失计时；亮度 / Laplacian 模糊 / 过曝 | 规则级 |

## 6. 时序、状态机与警报（三者正交）

### 6.1 引导状态 `GuideState` —— 只回答"路往哪走"

`NO_PATH`、`ALIGNED`、`DRIFT_LEFT`、`DRIFT_RIGHT`、`TURN_LEFT`、`TURN_RIGHT`、`PATH_LOST`

- 符号约定：`offset_m < 0`（盲道在左）→ `DRIFT_LEFT`（需向左靠）；
  `heading_deg > 0`（前方盲道右偏）→ `TURN_RIGHT`（需向右转）。两者都按"用户该往哪边走"命名。
- **滞回**：进入用 `*_enter`，退出用 `*_exit`，避免阈值附近来回跳。
- **去抖**：存在性需连续 `confirm_frames` 帧一致，撤销需 `release_frames` 帧；
  横向偏移与航向角走 EMA；砖型走多数投票。

### 6.2 警报 `Alert` —— 回答"现在该注意什么"

`WARNING_TILE`、`CROSSWALK`、`STAIRS`、`OBSTACLE_NEAR`、`LIGHT_RED`、`LIGHT_GREEN`

警报与状态**正交**，每帧可以有多条，按优先级抢占播报。

> **踩过的坑（必须记住）**：最初把提示砖做成 `GuideState` 的一个状态，
> 结果在 `Test.mp4` 上 **298/300 帧被 `WARNING_TILE` 占满**——因为提示砖常在
> 脚下（约 0 米），阈值 2.5 米就永远触发，转向与偏移信息全被吃掉。拆成正交的
> 警报后，同一段视频得到 14 个有意义的状态片段（平均 21 帧/段）。
>
> 由此还得到第二条规则：**提示砖在脚下（< 0.6 m）不算"前方有提示砖"，不报警**，
> 只置 `on_warning_tile` 标记。否则站在提示砖上会持续误报。

### 6.3 播报

- 警报优先于引导状态：有警报先报警报，没有才报"往哪走"；
- 每种事件**独立冷却**（转弯 3s、提示砖 8s、障碍 4s…），全局限速只约束最低间隔；
- **高优先级可抢占**全局限速（障碍 > 台阶 > 丢盲道 > 提示砖 > 转向 > 偏移）；
- **热循环内绝不调用 LLM**；LLM 完全可选、异步、默认关闭。

实测：`Test.mp4` 300 帧（约 20 秒）只播报 10 次，且每次都对应当前最该说的事。

## 8.5 调试服务与可视化（零新依赖）

用 Python 标准库 `http.server.ThreadingHTTPServer` 实现，不引入 FastAPI/Flask。

| 端点 | 用途 |
|---|---|
| `GET /` | 调试页面（`web/index.html`，无构建步骤） |
| `GET /stream.mjpg` | 带叠加的 MJPEG 实时画面（`?overlay=0` 取原始画面） |
| `GET /events` | SSE 推送逐帧 Scene JSON + 播报事件 |
| `GET /api/scene` | 最近一帧 Scene JSON（轮询兜底） |
| `GET /snapshot.jpg` | 当前带叠加的单帧 |
| `GET /health` | 运行状态、帧率、相机标定、最近错误 |
| `POST /source` | 切换帧源（本地视频 / ESP32 MJPEG / USB） |
| `POST /config` | 改标定与阈值，**就地生效、不重新加载模型** |
| `POST /reset` | 清空时序与播报状态 |

**取舍：叠加层画在服务端（Python）**，而不是浏览器 canvas。理由：任何客户端拿到的
画面都是同一份，不必重复实现绘制逻辑；代价是每帧多一次 `cv2.imencode`。
实测该开销约 3–5 ms/帧，在有服务（12.5 FPS）与无服务（10.5 FPS）的对比中落在
测量噪声内，**主循环帧率无实质下降**（验收要求 ≤20%）。

调试页单栏布局：左侧实时画面，右侧引导状态 / 警报 / 关键指标 / 播报时间线，
底部为帧源与标定控制，最下方是原始 Scene JSON。页面订阅 SSE，同时用 `<img>` 挂
MJPEG 流。

## 10. 已知限制（不可回避，需如实告知使用者）

1. `best.pt` 的 mAP50 仅 0.678 → 盲道召回上限由其决定，突破必须重训（需补数据）。
2. **ESP32 当前 `FRAMESIZE_QVGA`(320×240)，红绿灯仅几个像素，无法识别。** 需改 `FRAMESIZE_VGA` + `jpeg_quality=10` + `fb_count=2`；本设计提供独立 patch 文件，不修改原仓库。
3. 台阶检测只能给出"疑似"，不可作为唯一依据。
4. 纯 CPU 双模型约 70–80 ms/帧 → **约 12–14 FPS**（本机 32 核、YOLOv8n）。
5. 单目测距依赖地面平面假设，对悬空障碍（树枝、招牌）无效。
6. 标定参数（h / pitch / fov）不准会直接导致距离与偏移偏差，必须用标定工具校准。
7. 胸挂相机会拍到自己**的鞋/腿**，COCO 会识别成 `person`；已用三条规则过滤
   （近场距离、贴画面底边、person 宽高比）。**现场部署后仍需复核这条链路**。
8. 斑马线 / 红绿灯 / 台阶在现有素材上**无法给出准确率**，只有规则实现与单元测试，
   必须在真实现场采集数据后重新评测（`eval/label_tool.py`）。

## 11. 环境实测记录

- 训练指标（末轮）：mAP50 0.678 / mAP50-95 0.407 / P 0.751 / R 0.688
- `yolov8n.pt` COCO 权重可正常下载；相关类别索引：person 0、bicycle 1、car 2、motorcycle 3、bus 5、truck 7、traffic light 9、stop sign 11

### torch 线程数（重要，容易踩坑）

32 核 CPU 上实测 YOLOv8n 单帧推理（batch=1）：

| 线程数 | imgsz=320 | imgsz=640 |
|---|---|---|
| **1** | **15.8 ms** | **30.6 ms** |
| 2 | 21.3 ms | 65.9 ms |
| 4 | 18.7 ms | 45.2 ms |
| 8 | 13.7 ms | 31.7 ms |

**线程数越多越慢**——核多时默认线程数会严重争抢。因此 `torch_threads` 默认设为 **1**。
未设置时实测整条管线会从 ~50 ms/帧劣化到 ~90 ms/帧。

### 整条管线（含取帧）实测

`Test.mp4`（720×1280 竖屏）单模型：**p50 65.7 ms / p95 82.7 ms ≈ 15 FPS**。

双模型全管线（盲道 imgsz=640 + COCO imgsz=320 + 斑马线 + 台阶 + 状态机）：

| 阶段 | p50 |
|---|---|
| 盲道（YOLO 640 + 掩码 + LSD） | 52.0 ms |
| COCO（YOLO 320，障碍物 + 红绿灯共用一次推理） | 13.3 ms |
| 台阶 | 2.7 ms |
| 画面质量 | 2.3 ms |
| 斑马线 | 0.4 ms |
| 状态机 + 播报 | 0.1 ms |
| **合计** | **71.1 ms（p50）/ 88.5 ms（p95）** |

优化纪录：
- 颜色掩码限制最大处理面积 60k 像素（超限整数倍降采样）：7.9 ms → ~4 ms
- LSD 裁剪最长边限制 320 像素：19.9 ms → ~4 ms（门槛按对角线比例定义，等比缩放不改变结论）
- 画面质量评估先降采样到最长边 480：9.5 ms → 2.3 ms
- 障碍物与红绿灯**共用一次 COCO 推理**，而不是各跑一次

## 12. 踩过的坑汇总（按代价排序，便于后续复用）

1. **度量空间边界伪影**（代价最大）。度量网格中超出原图范围的行被填 0，直接对整条
   剖面做跳变/周期性分析时，"有效区边界"会被当成一个巨大阶跃。表现为台阶检测
   误报 **56/147 帧（38%）**，且报出的距离永远是网格边界值 1.78 m。修法是只分析
   有效像素的**最长连续行区间**（`largest_valid_span`），修完误报降到 **0/147**。
2. **torch 线程数过多反而变慢**。32 核上 threads=1 比 threads=2 快一倍以上。
3. **警报不能做成状态**。提示砖在脚下导致状态被占满 298/300 帧。
4. **`max_len_ratio` 不能当硬门限**。同一段行进砖在不同视角下该值 0.18–0.71 波动。
5. **负距离**。近景俯视时框底边投影到相机后方，Z 为负，必须截断到 0。
6. **`np.convolve(mode='same')` 零填充在首尾造出假梯度**，台阶检测要用 edge 填充。
7. **阴影 ≠ 台阶**。阴影只改亮度不改色相，加色相不变性可压掉这类误报。
8. **`from __future__ import annotations` 下 `dataclasses.field.type` 是字符串**，
   不能拿它做 `is_dataclass` 判断来反序列化嵌套 dataclass，必须显式构造。
9. **COCO 会把盲道大片纹理误认成行人**。实测出现过一个宽 717px、横跨整幅画面、
   占屏 34% 的 `person` 框（conf=0.72），播报出"前方 74 厘米有行人"。三条过滤
   缺一不可：近场距离（`ignore_below_m`）、贴住画面底边（`ignore_bottom_margin_px`，
   那是佩戴者自己的鞋/腿）、宽高比（`person_max_aspect`，人站着是瘦高的）。
10. **台阶 = 材质跳变，不只是亮度跳变**。阴影只改亮度不改色相，用色相不变性
   （`min_hue_jump_deg`）可以压掉这类误报；但"盲道砖边界"和"台阶"在单目地面
   平面上本质难分辨，这也是台阶只能报"疑似"的根本原因。
