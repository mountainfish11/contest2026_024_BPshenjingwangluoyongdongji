# 交接说明 · 盲人辅助设备视觉识别部分

> 这是可直接转交的独立包。**不需要原始参考资料（`材料/`）就能跑**，示例视频已放在
> `data/Test.mp4`。

---

## 1. 这是什么

一套 **CPU/GPU 可跑的实时视觉识别服务**：从 ESP32-S3-EYE 的 MJPEG 图传拉流，
识别盲道方向、砖型、障碍物、斑马线、红绿灯，输出结构化 JSON + 中文播报建议，
并带一个浏览器可视化调试台。

**核心设计**：把一切几何判断搬到**地面度量空间**——用针孔模型把像素反投影到地面，
得到真实的米和度，再算横向偏移、航向角、距离。而不是像参照实现那样用像素斜率凑。

## 2. 五分钟跑起来

```bash
cd 交付包

# ① 装依赖（CPU 版即可；有 N 卡时见第 6 节）
pip install -r requirements.txt

# ② 先自检环境：有没有显卡、torch 是什么版本
python -m vision_assist.cli --check-gpu

# ③ 用包内示例视频跑一遍（不接硬件）
python -m vision_assist.cli --source file:data/Test.mp4 --pitch 85 --height 1.3 --frames 60
```

要开调试台（浏览器看实时画面 + JSON）：

```bash
# 没有板子时，先把示例视频模拟成板子的流
python -m tools.mock_stream --video data/Test.mp4 --port 8099 --size 640x480

# 另一个终端
python -m vision_assist.cli --serve --source mjpeg:http://127.0.0.1:8099/stream --pitch 85 --height 1.3
# 打开终端打印出来的地址（默认 http://127.0.0.1:8760/）
```

> 注意示例视频 `data/Test.mp4` 是**手持手机近乎垂直向下拍的**，所以 `--pitch 85`。
> 真机的胸挂相机应该是 **25–35°**，必须重新标定（见第 6 节）。

## 4. 现在能做什么（诚实版）

| 能力 | 方法 | 精度等级 | 现状 |
|---|---|---|---|
| 盲道存在 / 范围 | YOLOv8n 自训模型 `blind_path.pt` | **模型级**，mAP50 0.678 | 可用，召回受模型上限限制 |
| 行进砖 / 提示砖 | LSD 长线段统计 | 规则级 | **8/8 标注样本全对**，有回归测试 |
| 横向偏移 / 航向角 | 地面反投影 + 鲁棒拟合 | 几何精确（依赖标定） | 可用 |
| 障碍物 + 距离 | YOLOv8n-COCO + 框底边反投影 | 模型级 | 可用 |
| 红绿灯状态 | COCO 框 + 框内 HSV + 时序投票 | 模型级检测 + 规则级颜色 | 实现完成，**无真实样本验证** |
| 斑马线 | 度量空间白条周期性 | 规则级 | 实现完成，**无真实样本验证** |
| 台阶 | 度量空间亮度跳变 + 色相不变性 | 规则级，只报"疑似" | 实现完成，**无真实样本验证** |

**斑马线 / 红绿灯 / 台阶没有准确率数字**——现有素材里没有这些目标。要真实数字必须
用现场实拍数据标注后重跑（工具在 `eval/label_tool.py`）。**不要编数字。**

## 5. 实测性能（RTX 4060 Laptop + VGA 输入）

| 指标 | 数值 |
|---|---|
| 板子出流 | 16–19 fps，9 KB/帧，约 175 KB/s |
| 处理帧率 | 15–18 fps（跟得上流，不跳帧） |
| 单帧延迟 | 25–35 ms（tactile ≈10ms + coco ≈11ms + 其他 ≈5ms） |
| 纯 GPU 前向 | 盲道 8.6 ms / COCO 9.1 ms |
| 纯 CPU（无 GPU） | 单帧 60–80 ms → 约 13–16 fps |

## 6. 拿到手**必须先做**的三件事

### ① 标定（影响正确性，比帧率重要得多）

不标定的话所有"米"都是错的。启动服务后，在调试页底部填：

- **离地高度**：卷尺量镜头中心到地面
- **俯仰角**：镜头低于水平线的角度（胸挂 25–35°）
- **水平视场角**：OV2640 约 65°，一般不用改

画面上有绿线（地面 1/2/3/5 米）和蓝线（正前方中线）。**调参数让绿线落在真实地面位置**，
比如让人站在正前方 2 米，`2.0m` 那条线应该正好在他脚下。对齐后点
「保存为 calibration.json」，以后启动加 `--config calibration.json`。

命令行也能标定（有桌面环境时弹窗调滑块）：

```bash
python -m tools.calibrate --source mjpeg:http://<板子IP>/stream --height 1.2 --pitch 30
```

### ② 烧固件到 ESP32-S3-EYE

见第 7 节。**当前板子若是旧固件，会有连接卡死问题。**

### ③ 确认 GPU 用上了

```bash
python -m vision_assist.cli --check-gpu
```

如果显示 `CUDA 编译版本: 无 —— 这是 CPU 专用版 torch`，说明装的是 CPU 版 PyTorch
（**即使机器有显卡也用不上**，这是最坑的一点）。换成 CUDA 版：

```bash
# 驱动 555 及以上，CUDA 12.4
pip install "torch==2.6.0+cu124" "torchvision==0.21.0+cu124" --index-url https://download.pytorch.org/whl/cu124
```

注意：最新的 torch 2.12 **没有 CUDA wheel**，最高只到 2.9.1。装完重开终端再 `--check-gpu`。

## 7. ESP32 固件（三个，都用 Arduino IDE）

| 固件目录 | 用途 | 烧录设置 |
|---|---|---|
| `esp32/camera_stream_download_vga/` | **主固件**：VGA 640×480 MJPEG 图传 | PSRAM=OPI PSRAM，USB CDC On Boot=Enable |
| `esp32/diag_serial/` | 串口+相机自检（先烧这个确认硬件） | 同上 |
| `esp32/uart_monitor/` | UART↔USB 串口监视/桥接工具 | 同上 |

**`PSRAM = OPI PSRAM` 必须设对**，否则 VGA + 双缓冲会初始化失败、板子反复重启
（串口会看到 `Camera failed, restart in 3s`）。

主固件相对原厂示例改了三处，都很关键：

1. **加 `Serial.begin()` + `logf()`**：原示例只用 `ESP_LOGI`，而它在 S3 上走 UART0
   的 GPIO43/44，不接 USB —— 所以插 USB 只能看到 ROM 横幅、看不到任何应用日志
2. **推流连接加 20 秒上限**：原代码 `while (cl.connected())` 在客户端异常断开后会
   卡在 `cl.write()` 等 TCP 重传超时（1–2 分钟），期间 `loop()` 完全跑不动，
   表现是"TCP 能连上但 /stream 和 /capture 都没响应"，只能断电
3. **`WiFi.setSleep(false)` + 40 秒连接等待**：关掉 WiFi 省电减少抖动

板子 IP 会变（AP 模式固定 `192.168.4.1`；连路由器/热点时由 DHCP 分配）。
不知道 IP 时用：

```bash
python -m tools.find_board
```

## 8. 代码结构（要扩展看这里）

```
帧进 ──> quality(画面质量)
      ──> tactile(YOLO + LSD 纹理)  ─┐
      ──> coco(YOLO 通用) ──> obstacles / traffic_light
      ──> crosswalk(度量空间周期性)
      ──> stairs(度量空间跳变，保守)
                                      ↓
                 temporal(跟踪 + EMA + 去抖)
                                      ↓
                 state(引导状态机，带滞回)
                                      ↓
                 alerts(警报，与状态正交) ──> events(优先级/冷却) ──> Scene JSON
```

### 加一个新检测器只要 4 步

1. 在 `vision_assist/detectors/` 新建 `xxx.py`，继承 `Detector`，实现 `process(ctx) -> 结果dataclass`
   （参考 `detectors/crosswalk.py`，它是最短的一个）
2. 在 `vision_assist/pipeline.py` 的 `Scene` 里加字段，在 `process()` 里调用
3. 如果要触发播报：在 `vision_assist/alerts.py` 里加一种警报，在 `config.py` 的
   `SpeechThresholds.priority` 和 `cooldown_s` 里登记
4. 在 `vision_assist/schema.py` 里加字段校验，在 `tests/` 加测试

**务必同时更新 `docs/设计.md`**——里面记着为什么这么设计、踩过哪些坑。

## 9. 输出协议（对接用）

`vision_assist/schema.py` 是唯一权威定义，版本 `1.0`，字段只增不改。

```json
{
  "state": "DRIFT_LEFT",
  "tracker": {"offset_m": -0.18, "heading_deg": -12.5, "present": true, "lost": false},
  "alerts": {"alerts": [{"kind": "OBSTACLE_NEAR", "priority": 100, "distance_m": 2.4, "detail": "行人"}],
             "on_warning_tile": false},
  "speech": {"text": "盲道偏左18厘米，向左靠一点", "spoke": true, "priority": 40},
  "latency_ms": {"total": 26.9}, "fps": 17.4
}
```

两条约定：

- **单位一律米和度**；`offset_m > 0` = 盲道在右，`heading_deg > 0` = 前方盲道向右偏
- 优先用 `tracker`（已平滑去抖），`tactile` 是单帧原始值，仅供排查

服务端点：`/stream.mjpg`（叠加画面）、`/events`（SSE 推 JSON）、`/api/scene`、
`/snapshot.jpg`、`/health`、`POST /source`、`POST /config`、`POST /config/save`、`POST /reset`。

## 10. 板子协议（要改传输方式时看）

**当前**：WiFi 802.11n 2.4GHz → TCP → HTTP/1.1 → MJPEG。

```
GET /stream
HTTP/1.1 200 OK
Content-Type: multipart/x-mixed-replace; boundary=f
                                ↑ 整个响应没有 Content-Length，靠连接关闭定界

--f\r\nContent-Type: image/jpeg\r\nContent-Length: 9216\r\n\r\n<jpeg>\r\n
--f\r\nContent-Type: image/jpeg\r\nContent-Length: 9130\r\n\r\n<jpeg>\r\n
```

相机侧：OV2640 硬件 JPEG，VGA 640×480，`jpeg_quality=10`，`fb_count=2`，PSRAM 缓冲。

**这个协议有三个短板**（改进方向）：

1. **单客户端**：板子 `WebServer` 是阻塞式的，浏览器和 Python 不能同时看流
2. **没有帧序号和时间戳**：所以端到端延迟测不出来，丢帧只能靠 TCP 推断
3. **丢包靠 TCP 重传**：重传会造成延迟尖峰

**建议的第一个改进**：给每帧加 8 字节头（`uint32 seq` + `uint32 millis`），
成本 0.09%，就能精确算出真实端到端延迟和真实丢帧率。

## 11. 已踩过的坑（省你几天）

按代价排序，完整版见 `docs/设计.md` 第 12 节。

1. **`HTTPResponse.read(65536)` 会阻塞攒满 64KB** → 板子一帧 9KB，等于每 7 帧才返回一次，
   整条管线被卡成 **4–5 fps**。必须用 `read1()`。这个坑极其隐蔽：用原始 `socket.recv`
   的探测工具能测出 22 fps，服务端却只有 4 fps
2. **Windows 的 `time.sleep()` 粒度是 15.6ms** → 用 sleep 轮询等帧每帧白等 100+ ms，
   要改用条件变量阻塞等待
3. **度量空间边界伪影** → 网格外无效行被填 0，"有效区边界"被当成巨大阶跃，
   台阶误报 38%，且报出的距离永远是网格边界值。要只分析有效行的最长连续区间
4. **torch 线程数越多越慢** → 32 核上 threads=1 最快，threads=2 慢一倍
5. **警报不能做成状态** → 提示砖在脚下会让状态被占满 298/300 帧
6. **`max_len_ratio` 不能当硬门限** → 同一段行进砖在不同视角下该值 0.18–0.71 波动
7. **COCO 会把盲道纹理认成行人** → 需要"近场距离 + 贴画面底边 + person 宽高比"三重过滤
8. **Windows `SO_REUSEADDR` 允许端口劫持** → 旧服务进程占着 8760，浏览器连到死服务上，
   页面永远"无新帧"而命令行看起来正常

## 12. 已知限制（不要美化）

1. `blind_path.pt` 的 mAP50 只有 **0.678**，盲道召回上限被它锁死。想突破只能重训，
   需要补标注数据
2. **ESP32 必须出 VGA**，QVGA 下红绿灯只有几个像素、远处盲道纹理全丢
3. **台阶只能报"疑似"**，置信度上限 0.6。单目在地面平面上分辨"砖缝"和"台阶"本质困难
4. 单目测距依赖地面平面假设，**对悬空障碍（树枝、招牌）无效**
5. 标定参数不准会直接放大误差，`pitch` 尤其敏感（差 5° 在 3 米处误差超半米）
6. 斑马线/红绿灯/台阶**没有真实数据验证过**
7. 板子出流约 16–19 fps 是当前链路上限，不是算法上限
